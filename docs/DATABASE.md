# Database Documentation

## Project

**LOOP — AI Customer-Feedback Intelligence Platform**

This document describes the database design, schema, relationships, seed data, migration workflow, and local setup used by the LOOP internship project.

## Technology

- PostgreSQL hosted on Neon
- Prisma ORM 6.19.3
- Prisma Client 6.19.3
- TypeScript
- Next.js 14
- Faker for realistic demo data
- bcryptjs for password hashing

## Database Architecture

LOOP is a multi-tenant application. Each company is represented by a `Workspace`.

Every tenant-owned record must be associated with a `workspaceId`. Application queries must always filter by the authenticated user's workspace to prevent cross-tenant access.

```text
Workspace
├── Users
├── Feedback
│   ├── FeedbackTheme
│   │   └── Theme
│   └── Embedding
└── Reports
    └── Generated by User
```

## Models

### Workspace

Represents one company or tenant.

Main fields:

- `id`
- `name`
- `slug`
- `createdAt`
- `updatedAt`
- `deletedAt`

Relations:

- Has many users
- Has many feedback records
- Has many themes
- Has many reports

Important constraint:

- `slug` is globally unique

### User

Represents a workspace member.

Main fields:

- `id`
- `name`
- `email`
- `passwordHash`
- `role`
- `workspaceId`
- `createdAt`
- `updatedAt`
- `deletedAt`

Roles:

- `ADMIN`
- `ANALYST`
- `VIEWER`

Relations:

- Belongs to one workspace
- Can generate many reports

Composite uniqueness:

```text
workspaceId + email
```

### Feedback

Stores customer feedback received from different channels.

Main fields:

- `id`
- `content`
- `channel`
- `sourceRef`
- `customerLabel`
- `sentiment`
- `sentimentScore`
- `featureArea`
- `classificationRationale`
- `classificationStatus`
- `classificationError`
- `status`
- `workspaceId`
- `createdAt`
- `updatedAt`
- `deletedAt`

Relations:

- Belongs to one workspace
- Can belong to many themes through `FeedbackTheme`
- Can have one embedding

Workflow status:

- `NEW`
- `REVIEWED`
- `ACTIONED`

Classification status:

- `PENDING`
- `PROCESSING`
- `COMPLETED`
- `FAILED`
- `MANUAL_REVIEW`

Sentiment:

- `POS`
- `NEU`
- `NEG`

Channels:

- `MANUAL`
- `CSV_IMPORT`
- `SUPPORT`
- `EMAIL`
- `SURVEY`
- `APP_STORE`
- `PLAY_STORE`
- `SOCIAL_MEDIA`
- `SALES_NOTE`

Important indexes:

- `workspaceId`
- `workspaceId + createdAt`
- `workspaceId + channel`
- `workspaceId + sentiment`
- `workspaceId + status`
- `workspaceId + classificationStatus`
- `workspaceId + deletedAt`

### Theme

Represents an AI-generated or manually maintained feedback theme.

Examples:

- Performance
- Payments
- Authentication
- Reliability
- Reporting

Main fields:

- `id`
- `name`
- `description`
- `color`
- `workspaceId`
- `createdAt`
- `updatedAt`
- `deletedAt`

Relations:

- Belongs to one workspace
- Connected to feedback through `FeedbackTheme`

Composite uniqueness:

```text
workspaceId + name
```

### FeedbackTheme

Join table for the many-to-many relationship between `Feedback` and `Theme`.

Main fields:

- `feedbackId`
- `themeId`
- `confidence`
- `createdAt`

Primary key:

```text
feedbackId + themeId
```

Purpose:

- Allows one feedback record to have multiple themes
- Allows one theme to be linked to many feedback records
- Stores AI confidence for each theme assignment

### Embedding

Stores the semantic-search representation of one feedback record.

Main fields:

- `id`
- `feedbackId`
- `vector`
- `model`
- `dimensions`
- `createdAt`
- `updatedAt`

Relations:

- Belongs to exactly one feedback record
- `feedbackId` is unique

Current implementation:

- The vector is stored as `Json`

Future implementation:

- This can later be migrated to PostgreSQL `pgvector` for efficient semantic similarity search used by Ask LOOP

### Report

Stores generated Voice-of-Customer reports.

Main fields:

- `id`
- `title`
- `periodStart`
- `periodEnd`
- `contentJson`
- `workspaceId`
- `generatedBy`
- `createdAt`
- `updatedAt`
- `deletedAt`

Relations:

- Belongs to one workspace
- Generated by one user

Important indexes:

- `workspaceId`
- `workspaceId + createdAt`
- `workspaceId + periodStart + periodEnd`
- `generatedBy`
- `workspaceId + deletedAt`

## Relationships

```text
Workspace 1 ──── * User
Workspace 1 ──── * Feedback
Workspace 1 ──── * Theme
Workspace 1 ──── * Report
Feedback * ──── * Theme (through FeedbackTheme)
Feedback 1 ──── 0..1 Embedding
User 1 ──── * Report
```

## Multi-Tenant Security Rule

Every database operation involving tenant-owned data must include the authenticated user's `workspaceId`.

Correct example:

```ts
const feedback = await prisma.feedback.findMany({
  where: {
    workspaceId: session.user.workspaceId,
    deletedAt: null,
  },
});
```

Incorrect example:

```ts
const feedback = await prisma.feedback.findMany();
```

A record ID supplied by the browser must never be trusted by itself.

Correct update pattern:

```ts
await prisma.feedback.updateMany({
  where: {
    id: feedbackId,
    workspaceId: session.user.workspaceId,
  },
  data: {
    status: "REVIEWED",
  },
});
```

Server-side authorisation is mandatory. Hiding buttons in the frontend is not sufficient.

## Delete Behaviour

- Deleting a workspace cascades to its users, feedback, themes, and reports
- Deleting feedback cascades to its feedback-theme links and embedding
- Deleting a theme cascades to its feedback-theme links
- Deleting a report generator user is restricted while reports still reference that user

Soft-delete fields such as `deletedAt` are used where the application may need to preserve data.

Queries should normally include:

```ts
deletedAt: null
```

## Environment Variables

Create a local `.env` file containing:

```env
DATABASE_URL="your-neon-postgresql-connection-string"
```

Never commit `.env`.

## Prisma Configuration

The root-level `prisma.config.ts` is used to configure Prisma.

```ts
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: process.env["DATABASE_URL"]!,
  },
});
```

## Team Setup

After cloning the repository, each teammate should run:

```bash
npm install
```

Then create their local `.env` file with the shared Neon connection string.

```bash
npx prisma generate
npx prisma migrate dev
```

Seed the shared demo data only when coordinated with the team:

```bash
npx prisma db seed
```

Because the team uses one shared Neon database, repeated seeding resets the demo workspace data. Team members should not run the seed command while someone else is actively testing that data.

## Migration Workflow

When the schema changes:

1. Update `prisma/schema.prisma`
2. Run `npx prisma format`
3. Run `npx prisma validate`
4. Create a named migration
5. Review the generated SQL
6. Test the migration
7. Commit the schema and migration
8. Open a pull request
9. Tell teammates to regenerate Prisma Client

Example:

```bash
npx prisma migrate dev --name add_feedback_priority
npx prisma generate
```

Commit:

```bash
git add prisma/schema.prisma prisma/migrations
git commit -m "feat(database): add feedback priority"
```

## Rules for Team Members

- Do not edit the Prisma schema without coordinating with the database owner
- Do not delete migration folders
- Do not modify an already-applied migration
- Create a new migration for every schema change
- Keep `prisma` and `@prisma/client` versions aligned
- Never commit `.env`
- Never expose the Neon connection string in screenshots, issues, or pull requests
- Always scope tenant-owned queries by `workspaceId`
- Always run `npx prisma generate` after pulling schema changes
